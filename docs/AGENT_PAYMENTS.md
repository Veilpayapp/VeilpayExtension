# Paying with an AI agent

Goal: a user types *"send 1 SOL to `<address>`"* into Claude and the wallet
executes it.

This document records the design as it was refined, including the options that
were rejected and why, because the rejections carry the security reasoning.

Two transports ship, and the difference is *who runs the server*:

| Mode | Setup for the user | Who hosts |
| --- | --- | --- |
| **Local** (`mcp/`) | run a Node command, paste a token | the user |
| **Relay** (`relay/`) | click Connect, sign in once | whoever deploys `relay/` |

The relay is the answer to "I don't want to run anything". See
[Zero-setup via a hosted relay](#zero-setup-via-a-hosted-relay).

---

## The constraint that shapes everything

A browser extension **cannot be reached inbound**. There is no port to open and
no URL to call. Any integration must be *initiated by the extension*. This one
fact eliminates most obvious designs.

Two more constraints from this repo:

- **Keys never leave the extension.** The vault decrypts into the service
  worker's memory and nowhere else. A bridge that reads key material is out.
- **MV3 kills the service worker when idle** (~30 s). So the service worker
  cannot hold a long-lived connection, and keeping it awake forever would defeat
  the idle-relock design.

---

## Iteration 1 — give the MCP server the key

An MCP server is a local Node process that Claude spawns. Simplest possible
design: it holds a private key and signs transactions itself.

**Rejected.** It creates a *second wallet*. Funds in the extension are
unreachable from a key in a JSON file, so the user would have to fund a new
address. It also puts an unencrypted key on disk next to an agent that reads
untrusted text, which is precisely the threat model this wallet exists to avoid.

## Iteration 2 — native messaging

Chrome's sanctioned extension↔native-app channel
(`chrome.runtime.connectNative`). The extension initiates, so the inbound
constraint is respected, and no network port is involved.

**Rejected for now, not forever.** It requires registering a host manifest in
the OS (on Windows, a registry key) plus installing a native binary. That is a
heavy, platform-specific install for a feature the user wants to "just work".
Worth revisiting as a hardened transport later, since it needs no open port and
no shared secret.

## Iteration 3 — localhost bridge, extension long-polls

The MCP server also runs a tiny HTTP server on `127.0.0.1`. The extension polls
it. The extension initiates every connection, so nothing is exposed inbound.

**Accepted.** Zero dependencies (`node:http` + `fetch`), zero cost, works on
every platform, and the transport is a loopback socket that the OS keeps off the
network. Long-polling (the server holds the request open until work arrives)
gives push-like latency with only an outbound request.

## Iteration 4 — who authorises the payment?

This is the crux. "The wallet does it automatic" is the feature *and* the
vulnerability: if an agent can move funds freely, then any page, email, or
document the agent reads can instruct it to drain the wallet. Prompt injection
is not hypothetical for an LLM that summaries untrusted text.

**Accepted design: a grant is the authorisation.** The user grants a spending
capability *once*, visibly, in the extension. The agent may then act
autonomously **inside** that envelope and nothing else. The repo already
implements this — `src/core/vap/` has grants with `maxPerOperation`,
`maxPerWindow`, `windowSeconds`, `approvalThreshold`, allowlists, rolling spend
windows, an audit ledger, and a pure `requiresApproval` decision function.

So the bridge is treated as **just another client**, exactly like a dapp:
the same `requiresApproval` gate, the same audit trail. **Pairing is the
consent gesture**: connecting (local token or hosted relay) creates a default
grant — 0.01 native units per payment, 0.1 per day, 90-day expiry, any chain —
so in-cap payments run silently from the first one, and anything larger is
refused by policy (the approval threshold sits at the window cap, so the grant
never defers to a prompt). The grant is listed and revocable under VAP Grants.

## Iteration 5 — hardening the transport

Accepted in principle, hardened in practice:

- **Bind `127.0.0.1` only**, never `0.0.0.0`.
- **Shared token**, generated by the MCP server, compared with
  `crypto.timingSafeEqual`. A local process cannot drive the wallet without it.
- **Idempotency key** on every send. An agent that retries a timed-out call
  must not pay twice.
- **Nothing executes stale.** Queued bridge requests older than five minutes are
  dropped rather than replayed later.
- **The poller lives in the offscreen document**, not the service worker. The
  offscreen document holds no key material, so it can hold the long-poll without
  keeping the vault's decrypted seed resident.
- **Off by default.** The bridge only runs if the user starts the MCP server
  *and* pastes the token into the extension.

## Zero-setup via a hosted relay

The local design above still asks the user to run a Node process and copy a
token. That is fine for a developer and wrong for everyone else. But the AI host
must be able to *reach* something, and an extension can never be that something —
so "just authenticate" requires a server with a public URL.

### Iteration 6 — hosted relay, extension dials out

`relay/server.mjs` is a deployable server with two faces:

- `/mcp` — a remote MCP endpoint. The user adds **one URL** to Claude and
  signs in with a device code. No local install at all.
- `/wallet` — a WebSocket the extension connects *out* to. Outbound-only from
  the browser's side, so no port, no tunnel, no localhost.

The relay pairs the two by an opaque wallet id. A tool call on `/mcp` is pushed
down the wallet's socket; the result comes back up the same socket.

### Iteration 7 — assume the relay is hostile

A hosted relay sits in the middle of every payment request, so it must be
assumed to be curious, buggy, or even malicious. The design treats it as
**untrusted**, which is what makes it acceptable for a third party to operate:

- It never holds key material, and cannot sign anything.
- It cannot forge a payment the user did not authorise, because the caps and the
  approval prompt are enforced **inside the extension** — the relay can only
  *ask*. A compromised relay is limited to spamming requests, which the prompt
  limiter and the user's own caps bound.
- It sees request metadata (amount, recipient) because it routes it. That is a
  real privacy cost, and the honest one to state: the relay learns what you pay.
  Running the local mode avoids it entirely.
- Wallet ids and device codes are random and short-lived; the wallet's socket is
  authenticated with a secret only the extension and the pairing response know.

### Iteration 8 — pairing without typing a token

Device-authorisation flow, the same shape as logging a TV into a streaming
service. Retained here for the local mode, where there is no public origin to
run discovery against:

1. Extension opens the relay and receives a **wallet id** and a short
   **pairing code** (`ABCD-1234`).
2. User adds the relay URL to Claude as a remote MCP server.
3. Claude initiates OAuth; the relay shows a page asking for the pairing code.
4. User types the code once. The relay binds the MCP session to that wallet's
   socket and issues an access token.

### Iteration 9 — kill the code entirely with OAuth discovery

The code in iteration 8 was still something to copy by hand, which is exactly the
friction this feature is supposed to remove. It also forced a choice between a
long-lived code and an awkward expiry.

**Shipped instead:** the relay advertises standard OAuth metadata, so the MCP
client discovers how to authenticate and runs the handshake itself. The wallet id
lives in the MCP URL's **path** (`https://relay/mcp/<walletId>`), so the URL the
user pastes already carries its identity and nothing else has to be typed. The
user's only action is approving one consent page.

Two details carry the security here:

- **PKCE S256 is required.** Without it, an intercepted authorization code is
  directly replayable. Codes are also single-use and expire in five minutes.
- **The path only *names* the wallet, never authorises it.** An unauthenticated
  call to `/mcp/<walletId>` is refused and answered with a `WWW-Authenticate`
  header pointing at the metadata document, which is what makes the client start
  OAuth rather than give up. Treating the id as a capability would have made the
  URL itself the credential.

### Iteration 10 — the button the user actually wanted

The remaining step was "find the connector settings page in your AI client".
The panel now shows a client choice (Claude / ChatGPT), copies the MCP URL to the
clipboard the moment it is minted, and opens that client's connector page.

**What is genuinely not possible:** pre-filling the connector. Neither vendor
documents a URL parameter that adds a remote MCP server, so the last step is one
paste. Anything claiming otherwise would be inventing behaviour they do not
publish.

### What the user actually does

1. Install the extension (already true).
2. Settings → Agent → pick Claude or ChatGPT → **Connect**.
3. The panel opens that client's connector page with the MCP URL already on the
   clipboard. Paste it.
4. The client shows the relay's consent page. Approve it.

Done. No Node, no `npm`, no token to copy by hand, and nothing to repeat on
reconnect.

### Honest limitation

Shipping this needs someone to **deploy `relay/` and own a domain**. That is a
real cost (a few dollars a month, or a free tier) and a real trust decision —
whoever runs the relay sees payment metadata. Nothing in this repository can
substitute for that, and I cannot deploy it for you. The code is written so the
operator can be anyone, including yourself.

## What this can and cannot do

**Read this before trusting it.**

- **Testnet only.** The wallet ships Sepolia, Solana devnet, and Stellar
  testnet. "Send 1 SOL" moves *devnet* SOL, which has no value. There is no
  mainnet path in this codebase.
- **The vault must be unlocked.** Agent payments require an unlocked vault, as
  every other signing path does.
- **It is a real spending capability.** Once a grant exists, anything that can
  reach the token can spend up to the caps without asking. Keep
  `maxPerWindow` and `approvalThreshold` small, and revoke grants you are not
  using. `list_grants` / `revoke_grant` exist for exactly that.

## Architecture

```
Claude / ChatGPT
   │  MCP over stdio (spawned as a child process)
   ▼
veilpay-mcp.mjs ────────────── long-poll ──────────────┐
   │  node:http on 127.0.0.1:8765                      │
   │  token-authenticated                              │
   ▼                                                   │
extension offscreen document (no key material) ────────┘
   │  chrome.runtime message
   ▼
service worker  ──  VAP grant check (requiresApproval)
   │                ├─ auto    → sign + broadcast
   │                └─ required → open approval popup
   ▼
Sepolia / Solana devnet / Stellar testnet
```

## Wire contract

Local bridge:

`GET /health` — unauthenticated. `{ ok, version, extensionConnected }`.

`GET /next` — long-poll, requires `x-veilpay-token`. Returns `{ id, tool, args }`
or `204` on timeout (25 s).

`POST /result` — requires the token. `{ id, ok, data?, error? }`.

Relay:

`POST /wallet/register` — the extension registers. Returns `{ walletId, secret }`;
the secret never leaves that pair.

`GET /next`, `POST /result` — the extension's authenticated long-poll
(`x-veilpay-wallet` + `x-veilpay-secret`).

`GET /.well-known/oauth-authorization-server`, `GET /.well-known/oauth-protected-resource`
— discovery, so an MCP client drives the handshake without user instruction.

`POST /register` — dynamic client registration.

`GET /authorize`, `POST /authorize/approve`, `POST /token` — the consent page and
the PKCE (S256, single-use code) exchange.

`POST /mcp/<walletId>` — remote MCP. Requires a bearer token; the path only names
the wallet, it does not authorise it.

Tools on both: `status`, `accounts`, `balance`, `send`, `grants.list`,
`grants.revoke`.
